# 事故 → 闸门（fw-lessons）

## 这份技能是什么、不是什么

**是**：把已经付过代价的失败，变成下次交付前能逐条勾选的闸门。
**不是**：变更日志，不是自我检讨，不是「最佳实践摘抄」。

方法借鉴一份工程事故复盘文档。它的价值不在记了多少坑，而在**每个坑都被迫产出一条能提前拦住同类坑的判据**。本技能把那套写法移植到固件生成链路：写法的统一格式是「现象 → 根因 → 处置 → 怎么提前发现」，最后一格必须是判据编号，不能是「以后注意」。

三条阅读线索：

- **交付前只想快速过一遍** → 直接看 `references/CRITERIA.md`，逐条打 PASS / FAIL / N/A。
- **遇到「测试都过了但行为不对」** → 看 `references/LESSONS.md` §3 验证类假象，这一类坑的共同点是绿灯不等于对。
- **出现了清单没拦住的新失败** → 看下面 §5 闭环规则，把这次失败变成一条新判据。

## 1. 四段式归因法

每条事故记录 `Lxx`，四段缺一不可：

| 段 | 要求 | 反例 |
|---|---|---|
| 现象 | 写可观测的具体表现，含原始报错/数值 | 「不太对」「有点问题」 |
| 根因 | **写机制**，不写态度。要能回答「为什么现有检查没拦住」 | 「不小心」「没注意」「疏忽」 |
| 处置 | 写实际改了什么，以及改完如何确认生效 | 「已修复」「后续加强」 |
| 怎么提前发现 | 必须落到 `CRITERIA.md` 的一条编号 `Cxx` | 「以后仔细检查」 |

**按根因归类，不按时间、不按模块**。同一根因的两次爆发合并到一张表；根因不同的两次失败，哪怕症状一样也要拆开。每条 `Cxx` 必须能反查到至少一个 `Lxx`，每条 `Lxx` 至少产出一条 `Cxx`。

根因写不深，闸门就拦不住。判断标准：把这条根因读给一个没经历过该事故的人，他能不能自己推出那条判据。

## 2. 证据分级（E0–E4）

本团队所有结论必须带等级标签。**推断写成实测口吻，是本技能要消灭的第一类事故。**

| 级别 | 含义 | 可写成 |
|---|---|---|
| **E0** | 推断 / 凭记忆 / 未验证 | 「待验证（E0）：……」 |
| **E1** | 静态检查：lint、静态分析、字段对照、代码阅读 | 「静态核对（E1）：……」 |
| **E2** | 主机侧真实执行：`cmake --build`、Unity 单测、模板渲染测试 | 「主机验证（E2）：……」 |
| **E3** | 目标板实测：烧录、串口启动序列、任务心跳、示波器/逻辑分析仪 | 「上板实测（E3）：……」 |
| **E4** | 独立回读：复位后读版本号、备份寄存器、flash 回读比对 | 「回读确认（E4）：……」 |

规则：

- **外部执行的返回值不能自证**（OTA 说 success、烧录说 OK、`validate` 说 valid），必须有独立回读才算 E4。
- 证据要能追溯：写 `文件:行号` 或命令与原始输出，不写「已确认」。
- E0/E1 **不得**用于支撑「可以上板 / 可以交付 / 已修复」这类结论。
- 实测后**必须回头改掉**此前标 E0 的那句话，不要让文档里同时留着推断和事实。

## 3. 闸门：交付前必须走

由主理人在 Phase 6 执行，`references/CRITERIA.md` 是唯一清单。

1. 逐条标 **PASS / FAIL / N/A**；N/A 必须写原因（环境不具备 / 不适用 / 已列欠账）。
2. 每条 PASS 要写证据路径；没有证据的 PASS 视同 FAIL。
3. 存在任一 FAIL → 不得进入交付，退回对应 Phase。
4. N/A 项汇总进 `LESSONS.md` §5 已知欠账表。
5. 报告正文附**闸门结果表**与**证据等级分布**，让读的人一眼看出哪些结论只是推断。

## 4. 验证类假象（最高优先级知识）

范本作者把「看到的不等于发生的」标为全篇最有价值的一节，本团队同样如此。固件链路的绿灯尤其廉价：编译器管语法不管引脚复用，主机测试管逻辑不管中断并发，串口有输出不代表调度跑起来了。

完整对照表见 `references/LESSONS.md` §3，闸门编号 C41–C48。一句话总纲：

> **任何一层检查通过，只证明那一层的模型成立，不证明被检查对象在真实硬件上的行为成立。**

遇到「全绿但现象不对」，先查这一节，不要重新怀疑代码、也不要重跑同一套测试。

## 5. 闭环：新失败如何变成机制

清单没拦住的失败，才是真正需要记录的东西。主理人在收尾时执行：

1. 按 §1 四段式追加一行到 `references/LESSONS.md` 对应根因分组，分配新 `Lxx`。
2. 在 `references/CRITERIA.md` 新增一条可勾选的 `Cxx`，注明来源 `[Lxx]`。
3. 两者编号互指；若该根因已存在但判据表述太窄，**改判据而不是只加事故**（说明旧的为什么漏了）。
4. 若这次失败属于「验证类假象」，同时补进 §3 对照表。
5. 已修复的项**从 §5 欠账表删掉** —— 欠账表不是历史陈列，修完留着会让人以为还没修。

闭环是否完成的判据：下一次有人遇到同类现象，能不能在 `CRITERIA.md` 里找到一条能提前拦住它的勾选框。找不到，就说明这次只记了事故、没提炼出机制。

## 6. 反模式

- 把清单写成按时间排列的流水账，或攒成一堆「注意事项」。
- 判据写成「确保 XXX 正确」这类无法判真假的话；必须是能回答是/否的问句。
- 一条判据合并两个根因不同的事故。
- 写「已检查」却不给证据路径；写「未验证」却不列进欠账表。
- 为了让闸门全绿而把 FAIL 改成 N/A。
- 把推断与实测混在同一句结论里。

## 7. 与 ub-mode 的边界

| | `ub-mode` | `fw-lessons` |
|---|---|---|
| 管什么 | 代码/模板**怎么写**（TDD、根因修复、小步提交） | 结果**怎么证明**、错了之后团队**怎么变聪明** |
| 何时生效 | 改动代码时默认生效 | 交付前、绿灯可疑时、出现新失败时 |
| 冲突时 | 服从事实性约束 | **优先** |

两者共用同一条底线：**不编造证据**。ub-mode 禁止编造质量门分数，本技能禁止编造证据等级与闸门结果。主理人按 `skills/ub-mode/references/embedded-adaptation.md` 的效力顺序裁决，并把取舍写进交付日志。
