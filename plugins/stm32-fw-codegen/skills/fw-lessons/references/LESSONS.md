# 事故、根因与闸门

这份文档记录的是**本专家团与其领域来源（hw2c / hw2c-web）真实付过代价的失败**，以及从每次失败里提炼出的判据。
它不是变更日志，也不是自我检讨：写法统一成「现象 → 根因 → 处置 → 怎么提前发现」，最后一格必须落到 `CRITERIA.md` 的编号。
用途是让下一次遇到同类现象时先查这里，而不是重新怀疑一遍生成结果。

**按根因归类，不按时间。** 每一行的根因都能对应到 `CRITERIA.md` 里的一条判据；反过来，每条判据都能反查到至少一次真实事故。
事故编号 `Lxx`，判据编号 `Cxx`，证据等级 `E0–E4` 的定义见 `../SKILL.md` §2。

三条阅读线索：

- 只想避免踩坑 → 直接看 [§5 已知欠账](#5-已知欠账) 与 `CRITERIA.md`。
- 遇到「测试全绿但行为不对」 → 先看 [§3 验证类假象](#3-验证类假象绿灯不等于对)，这是全篇最有价值的一节。
- 要改配置、发版或上架 → 看 [§1 判断与事实](#1-判断与事实) 和 [§4 可复用的验证手段](#4-可复用的验证手段)。

## 1. 判断与事实

这一节记的不是代码缺陷，是**判断和操作**的问题。它们比 bug 贵，因为 bug 有测试兜底，判断错了没人兜。

| ID | 现象 | 根因（机制） | 处置 | 怎么提前发现 |
|---|---|---|---|---|
| L01 | 平台解析失败：`members[0].name 的 en/zh 均为必填`，整包无法上架 | 6 个 `members[]` 用 `displayName`，是把**顶层**字段名类推到嵌套结构；而 `validate_expert.py` 不校验这个字段的拼写，本地全绿制造了虚假信心 | 6 处改为 `name`；深度 lint 补上 `members[].name` 校验；把「嵌套结构不共享顶层字段名」写进长期规则 | C01、C02 |

### 2.3 初始化顺序与硬件语义

| ID | 现象 | 根因（机制） | 处置 | 怎么提前发现 |
|---|---|---|---|---|
| L30 | FreeRTOS ARMv6-M 出现 `ulCriticalNesting` 毒值 `0xAAAAAAAA` | 调度器启动前的初始化顺序错；逐处打补丁只是在掩盖顺序问题 | 修**初始化顺序**（tick / 中断依赖），不打补丁；组件 `init` 可重复调用 | C31 |
| L31 | 中断反复进入，CPU 被同一个 ISR 吃满 | ISR 只清了它处理的那一个标志，其余标志仍挂起 | 逐个 ISR 核对「负责的全部标志」是否都清掉 | C32 |

| L33 | CRC 校验互相对不上，两端代码都「用的 CRC-16」 | CRC-16/CCITT-FALSE 与 CRC-16/XMODEM 名称撞车，多项式与初值不同；只写通名等于没定义 | 写全名 + 多项式 + 初值 + 是否反射；总线名、引脚名逐字一致，不做大小写归一化 | C34 |

| L35 | 看门狗喂狗周期、任务周期、串口日志行宽预算各自都「合理」，合起来却丢日志/触发复位 | 三层预算分三次加，没人把三个数放在一起比；改一层不重算另两层 | 把预算关系写成不变量：行宽 × 波特率 < 任务周期 < 喂狗窗口，改动任一层重算另两层 | C36 |
| L36 | 为抽象引入堆分配 / 动态分发 / 浮点格式化，在 Cortex-M0+ 上开销失控 | 通用设计建议没有经过目标内核约束过滤 | 禁堆分配、禁动态分发、禁浮点格式化；性能与精度影响标注为待验证 | C33 |

## 3. 验证类假象：绿灯不等于对

**全篇最有价值的一节。** 共同特征是：编译通过、单测全绿、静态检查干净、接口返回成功，但功能是坏的。
固件链路尤其容易中招，因为每一层检查验证的是**自己的模型**，不是硬件行为。

| ID | 看到的 | 实际 | 现在的做法 |
|---|---|---|---|
| L41 | `cmake --build` 成功、0 warning | 编译器只管语法与链接，不管引脚复用、时钟树、中断优先级配得对不对 | 引脚三层校验 + `arm-none-eabi-nm` / `.map` 核对符号与段地址 → C41 |
| L42 | 主机 Unity + Mock-HAL 单测全绿 | mock 没复刻生产语义（总线名 `strcmp` 大小写敏感、寄存器副作用），或 ISR 是空桩 | mock 必须与生产语义逐项比对；硬件/中断路径标「需上板验证」，不写假绿灯 → C42 |
| L43 | 模板渲染完成、工程目录里文件齐全 | 生成的 C 可能缺分号、宏展开错误、条件块内 `{% set %}` 没泄漏到块外 | 真跑 `cmake --build`，不以「文件生成了」当成功 → C43 |
| L44 | cppcheck 干净、静态检查 0 warning | 工具规则覆盖度有限，不等于 MISRA C:2012 合规 | 人工逐条核对并**列出未覆盖规则** → C44 |
| L45 | 串口有输出、能打印 banner | 可能只有一个任务在跑，调度、优先级、事件队列都没被验证 | 附启动序列原文 + 各任务心跳 → C45 |
| L46 | OTA 返回 success、写入完成 | 双槽 A/B 切换可能压根没生效；返回码是执行端的自述 | 复位后回读 `fw_version` + TAMP 备份寄存器（BKP0R `0x4000B100` 等） → C46 |
| L47 | 日志里一条 ERROR 都没有 | 失败被 catch 成文案、或被管道吞了退出码；所有调用都是「成功」 | 看调用频率与间隔；失败分支必须落 warning 与错误类别 → C47 |
| L48 | 本地 `validate_expert.py` + 深度 lint **全绿** | 平台解析仍可因 `members[].name` 失败（L01 真实发生） | 本地校验器不等于消费方；上架前按平台规则逐字段对照 → C48、C02 |
| L49 | 报告写「已验证可上板」 | 实际只跑过主机侧 E2，或只是推断 E0 | 每条结论带 E0–E4 标签，附证据路径 → C08 |

一条总纲：**任何一层检查通过，只证明那一层的模型成立，不证明被检查对象在真实硬件上的行为成立。**

## 4. 可复用的验证手段

这些是踩坑后摸索出来、验证过确实能提前发现问题的做法。

**引脚三层校验**：原理图/网表 → 器件模型 YAML → 生成代码，逐层比对同一个引脚，不跳层推断。

**派生值中段插桩**：在真实调用链的中间环节观测派生结果（`project.version` → banner / 镜像头），不只测输入与输出两端。

**编译产物核对**：`arm-none-eabi-nm <elf>`、`.map` 文件核对关键符号、段地址与栈/堆预留；这一步能拦住「编译过了但链接脚本错」。

**上板取证**：启动序列原文输出（不改写、不摘要）、各任务心跳、pyOCD 烧录后复位回读；无物理调试器时如实写「未验证」，不推测。

**外部执行独立回读**：烧录、OTA、注册这类「外部执行」，返回值不能自证，必须有第二次独立读取（复位回版本号 / 解压回读 zip 内 `plugin.json`）。

**两处比对要比 blob 不比工作区文件**：Windows 工作区 CRLF 与服务器 LF 会给出假的差异；用 `git show HEAD:path | md5sum` 对比线上 `md5sum`。

**清理探测现场**：验证用的线程、临时会话、探针产物按前缀识别后删除，避免污染真实数据（本团队收紧为：**只报告可清理项，不删除任何文件**）。

**分层预算一起比**：看门狗窗口、任务周期、串口行宽预算三处数字放在同一张表里比大小，改一层重算另两层。

以下为**有意识留下、尚未闭环**的项。**修掉之后请删掉对应行**，不要让清单变成历史陈列。

## 6. 代价盘点

最贵的几类失败，共同点是**都通过了「本地 / 静态 / 主机侧」这一层，都没通过「真实跑一遍」**：

1. **L01 嵌套字段名错误** —— 本地 validate 与深度 lint 全绿，平台解析直接拒绝，是唯一一次**阻断上架**的失败。排查成本高是因为「本地全绿」与「平台不接受」看起来矛盾，实际是两套校验器覆盖范围不同。
2. **L20 静默降级** —— 用户能拿到一份看起来完整的残缺工程，日志里没有任何异常。症状离根因最远，只能靠「失败与成功是否长得一样」这类结构性反问提前发现。
3. **L30 初始化顺序** —— 毒值出现在很远的地方，最容易诱导人逐处打补丁；补丁越多，真正的顺序问题越隐蔽。
4. **L42 结构盲区** —— `TEST` 构建的 ISR 空桩让主机测试**结构上不可能**测到中断缺陷，绿灯反而掩盖了风险。它不制造任何错误日志。

所有事故均为内部返工，未造成外部数据或设备损害。但 L01 说明一件事：**校验器本身也是被检查对象** —— 它说通过，只证明它检查过的那些维度通过。
